# UWP window integration

The native UWP host demonstrates a CoreWindow and D3D11 swap chain. It does not yet run Horizon's window or game loop. The current game assumes that winit owns the application window and loop:

- `crates/horizon-client/src/game.rs` implements `ApplicationHandler` for both the loading state and game state. Both create an `Arc<winit::window::Window>` in their `resumed` handlers. The ready game handles keyboard, mouse, resize, focus and redraw events and uses `ActiveEventLoop` to schedule frames and exit.
- The normal entry point runs a winit event loop and transfers the loading state to the game state on that same window. The loop's `about_to_wait` also drives server shutdown, resource loading, controller polling, redraw requests and save completion.
- `crates/horizon-client-render/src/gfx.rs` accepts `Arc<Window>`, uses its display handle, creates and recreates a wgpu surface from it, and queries the window for size and presentation. The compositor also takes `Arc<Window>`. A replacement must cover these paths, including surface recreation and loading, not just the first render.
- winit 0.30.13's Windows implementation in `src/platform_impl/windows/event_loop.rs` registers a Win32 window class, creates a message-target HWND and dispatches `PeekMessageW`. Its public Windows backend does not adopt the UWP CoreWindow held by our host. A packaged desktop binary alone does not provide this UWP integration.
- An isolated release probe calling `EventLoop::new()` compiled for `x86_64-uwp-windows-msvc` with desktop SDK library paths. Its PE has the AppContainer flag, but its imports still include `user32.dll` `RegisterClassExW`, `CreateWindowExW` and `RegisterRawInputDevices`. This demonstrates that a successful Rust target build does not itself establish UWP window compatibility. The probe has not been run as a packaged app.
- `raw-window-handle` 0.6 has a WinRT handle, but that alone does not make this path work: the original wgpu-hal DX12 `instance.rs::create_surface` accepts a Win32 handle and rejects other raw handles; its GLES EGL/WGL paths similarly handle Win32 windows. An experimental EGL/ANGLE backend for UWP is being investigated separately. wgpu 30 also exposes a distinct unsafe DX12 `SwapChainPanel` surface target; using that would require a XAML panel and additional integration, and does not provide D3D11.

Two approaches are plausible. A UWP platform implementation in a winit fork could preserve more existing Horizon call sites, but must implement the `Window`, event loop, input, and lifetime contracts needed by Horizon. Alternatively, Horizon can extract an application-facing window/event interface, adapt both loading and game states to it, and implement an adapter driven by the UWP host's `CoreDispatcher`. Either approach still needs a wgpu backend able to present to the chosen UWP surface, or a separate renderer.

For an incremental implementation, first define ownership and lifetime of the CoreWindow and graphics surface on the UWP UI thread; then translate activation, suspend/resume, size, focus, keyboard, pointer, and close events; then drive the loading state and its worker; finally run the game state with redraw and save/shutdown semantics. Store game data in the app's writable storage and make prepared assets available there or through package assets. Test this integration separately from the current solid-color host and from backend feature support.
