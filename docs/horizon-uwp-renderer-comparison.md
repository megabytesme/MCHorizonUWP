## Renderer selection and profiles

Official Win32 Auto tries Vulkan → DX12 → GL on x64 and DX12 → Vulkan → GL on ARM64. Users can select a graphics API for the next launch. Vulkan is the reference for compute-driven terrain culling. The official source builds OpenGL and DX12 alongside Vulkan and offers no DX11 backend. UWP uses a XAML `SwapChainPanel`, packaged backends and a launcher surface probe. The bridge sets `WGPU_BACKEND` from the launch selection, which takes precedence over the in-game API preference. The host's separate experimental native D3D11 label is a different path from the wgpu D3D11 game tested here. ### FSR 3.1 frame generation

The setting controls the WGSL port of FSR 3.1 optical flow and frame interpolation. It renders a real world texture, computes 8×8 block motion and interpolated frames, adds hand/HUD overlays, and sends generated and real frames to a paced presenter. Its temporal upscaling peer is Horizon's TAA upscaler. They are separate code paths. The UI setting remains selectable and serializes `frameGeneration`. The interpolation branch also needs a matching SDR frame format or layered HDR, a usable copy-destination surface, and a gameplay frame without title, blur, classic post passes or native frame executor. Interpolation uses compute pipelines and storage textures, including signed `Rg32Sint` for optical flow. `gfx.rs:6852–6859` declines the compatibility path before frame setup, and `:8007–8043` handles the per-frame gates. [Official FSR design](https://github.com/horizon-rust/horizon/blob/0a875da91dbb0fdcb7ba8c42c11341aa229af51a/docs/graphics.md#L152-L154) · [Official optical flow implementation](https://github.com/horizon-rust/horizon/blob/0a875da91dbb0fdcb7ba8c42c11341aa229af51a/crates/horizon-client-render/src/gfx/frame_gen/optical_flow.rs#L168-L227)

- **D3D12 (C)**. The HAL advertises `COPY_DST` for the composition swapchain. The UWP build retains the engine presenter and compute path. Signed world and format availability establish the prerequisite only. Record real/rendered versus generated present counts, generated-frame images and a known movement target, first with SDR, then with HDR, shader packs and the two anti-aliasing paths.
- **D3D11 (S)**. `set_frame_generation` drops the saved On value before allocation. The public projection offers no compute, and its BGRA composition surface offers color target and optional copy-source only. Raising the native driver feature level leaves these three gates in place.
- **ANGLE (S)**. GLES swapchains in this HAL offer color-target usage only. The x64 receipt also records GLES 3.0 and zero storage-binding bytes. Removing the surface gate would still leave a compute/format and presenter gap on the observed context.

### HDR and presentation

Official Win32 DX12 reads a live output report from the HWND's monitor. HDR On configures HDR10 (PQ) or scRGB when output and layered float frame are eligible. Auto additionally requires the system report to say HDR is active. Black level, brightness, paper white, UI brightness, color boost, Look and calibration affect their associated curve, HUD plane or output parameters in the eligible frame. ## Terrain and GPU work

Cave, frustum, CPU entity and particle culling are engine logic and have different gates from GPU-driven draw generation. Official GPU Culling requires count draws, compute, eight storage buffers, and a compatible section layout. DX12 is gated on the normal pulled/flat-page terrain path because count draws lose the base vertex in `vertex_index`. The gate checks that layout. D3D11's public projection has no indirect execution and zero compute/storage limits. ANGLE is excluded by the GL multi-draw path and the GLES 3.0 test device lacks compute. GPU Culling has its own explicit reason in the UI. Translucent Batching needs indirect execution with base-vertex and first-instance support, and rejects GL. D3D11's renderer therefore still encodes its CPU draw lists. DX12's normal batching path remains source evidence pending an instrumented comparison. A classic terrain pack or native shadow pack can change layout and force CPU or alternate draws. [Official terrain path](https://github.com/horizon-rust/horizon/blob/0a875da91dbb0fdcb7ba8c42c11341aa229af51a/crates/horizon-client-render/src/gfx/gpu_culling.rs#L514-L568) · [Official graphics guidance](https://github.com/horizon-rust/horizon/blob/0a875da91dbb0fdcb7ba8c42c11341aa229af51a/docs/graphics.md#L58-L70)

The Mipmap Levels path updates views of the texture array or compatibility sprite sheet and caps levels by sprite geometry and existing allocations. Distant Plant Dither triggers a resource reload and CPU mip rebake. Far LOD terrain uses shared generation and upload with a 128-chunk ceiling when the adapter is classified as a non-Apple integrated GPU. The renderer audit has source evidence for these paths. It needs controlled texture, resource and far-terrain captures to isolate individual visible effects.
